## ۱. خلاصه‌ی تصمیم (Decision Summary)

یک **صفحه‌ی کنترل وب یکپارچه (Unified Web Control Plane)** ساخته می‌شود که تمام سطوح عملیاتی موتور کسب‌وکار را در یک رابط واحد جمع می‌کند: تأییدهای انسانی (HITL)، تلمتری و گیت‌ها، موجودی و محصولات، اتوماسیون‌ها، موتور هوش مصنوعی، سفارش‌ها و تنظیمات.

این تصمیم **معماری، پشته‌ی فناوری، استانداردهای طراحی و نقشه‌ی راه فازی** را تثبیت می‌کند. این تصمیم **هیچ مجوز اجرا، اتصال زنده، اعتبارنامه یا استقرار تولیدی صادر نمی‌کند**؛ هر مرحله‌ی اجرا تحت گیت مالک (D-139، D-045) باقی می‌ماند.

### چرا این تصمیم لازم است

- امروز نمای وضعیت فقط یک داشبورد ایستای فارسی است (`dashboard/index.html` + `dashboard/state_summary.json`) که صرفاً یک snapshot می‌خواند؛ هیچ عملیات، تأیید یا مشاهده‌ی زنده‌ای در آن وجود ندارد.
- موتور در وضعیت **Launch Candidate تأییدشده** است: Stages A–H تأیید شده و برنامه‌ی Live Wiring (Phases 5–18) با امضای مالک (D-170) بسته شده است. نقطه‌ی اتصال بعدی، یک **سطح کنترل عملیاتی** است.
- بدون یک Control Plane، تأییدهای انسانی (HITL)، گیت‌های fail-closed و رویدادهای تلمتری فقط از طریق CLI قابل مشاهده‌اند — که برای عملیات روزمره‌ی کسب‌وکار کافی نیست.

## ۲. معماری هسته (Core Architecture)

| لایه | انتخاب | دلیل / قید |
|---|---|---|
| Frontend | **Next.js (App Router)** + React Server Components | رندر سمت سرور، مسیرهای تودرتو، جریان داده‌ی صریح؛ بدون state مبهم سمت کلاینت |
| Styling | **Tailwind CSS** + توکن‌های معنایی (semantic tokens) | ممنوعیت hex خام در کامپوننت‌ها؛ توکن‌ها تنها منبع رنگ |
| Components | **Shadcn UI / Radix Primitives** | دسترس‌پذیری داخلی (focus management، aria)، قابل کپی و مالکیت‌پذیر در مخزن |
| Data Access | اتصال مستقیم به **canonical PostgreSQL** (D-055) | منبع حقیقت واحد؛ فقط نقش read-mostly با دسترسی محدود و fail-closed |
| Orchestration | **n8n webhook** (D-004، D-155) | هر کنش تغییردهنده از مسیر وب‌هوک امضاشده عبور می‌کند؛ رابط هرگز منطق کسب‌وکار را دوباره پیاده نمی‌کند |
| Caching / Queue | **Redis** (broker/cache) | صف‌ها، وضعیت زنده، نرخ‌محدودسازی نمایشی |
| Security | **Fail-Closed** | نبود شواهد = شکست؛ نه «گذر». نبود توکن = رد. خطا = توقف، نه ادامه |
| Observability | اتصال به لجر D-121 (`engine.log.v1`) | هر کنش رابط یک رکورد قابل ردیابی تولید می‌کند (D-121 trace context) |

### ۲.۱ مرزهای اقتدار (Authority Boundaries)

- **رابط، مرجع نیست.** Control Plane فقط نمایش می‌دهد و درخواست می‌سازد؛ حقیقت در canonical PostgreSQL و لجر رویداد (D-026/D-027) است.
- **هیچ کنش تغییردهنده‌ای بدون توکن مالک.** تأییدهای HITL از همان موتور توکن یک‌بارمصرف (D-146) استفاده می‌کنند؛ رابط توکن نمی‌سازد و کلید امضا ندارد.
- **هیچ نوشتن مستقیمی در SSOT از سمت رابط.** نوشتن فقط از طریق سرویس‌های canonical یا وب‌هوک n8n.
- **همه‌ی خروجی‌ها redacted.** طبق D-114/D-124 هیچ اعتبارنامه، توکن، PAN، آدرس یا داده‌ی شخصی در پاسخ‌ها و لاگ‌ها ظاهر نمی‌شود.

### ۲.۲ قید Fail-Closed

| وضعیت | رفتار رابط |
|---|---|
| داده‌ی گیت موجود نیست | نمایش **UNKNOWN / NO_DATA** با رنگ هشدار — هرگز سبز |
| داده‌ی گیت کهنه (stale) است | نمایش **STALE** با زمان آخرین اعتبارسنجی |
| خطای اتصال به PostgreSQL | نمایش وضعیت قطع + غیرفعال‌سازی کنش‌های وابسته |
| خطای وب‌هوک n8n | رد کنش با پیام صریح؛ بدون retry پنهان سمت رابط |
| نبود توکن تأیید | کنش غیرفعال (disabled) با توضیح دلیل |

## ۳. استانداردهای سیستم طراحی (Design System Standards)

مبنای اجباری: `.claude/skills/ui-ux-pro-max` (نسخه ۲.۱۳.۰). هر مقدار زیر **قید قابل آزمون** است، نه پیشنهاد سلیقه‌ای.

### ۳.۱ چیدمان RTL و تایپوگرافی

- **RTL سراسری:** `dir="rtl"` روی `<html>`، `lang="fa"`؛ آینه‌سازی کامل چیدمان، آیکون‌های جهت‌دار و نوارهای پیشرفت.
- **فونت:** `Vazirmatn` با fallback به `system-ui`؛ بارگذاری با `font-display: swap` (سابقه: `dashboard/README.md`).
- **مقیاس تایپوگرافی:**

| نقش | اندازه | وزن | line-height |
|---|---|---|---|
| Display / KPI | 30–36px | 700 | 1.2 |
| Heading (h2/h3) | 20–24px | 600 | 1.3 |
| Body | 16px | 400 | **1.5** |
| Label / Meta | 14px | 500 | 1.4 |
| Caption | 12px | 400 | 1.4 |

- **قید:** متن بدنه هرگز کوچک‌تر از ۱۶px نباشد؛ متن زیر ۱۲px ممنوع (pro-rules / §6).
- **ارقام:** نمایش ارقام فارسی در متن روایی؛ ارقام لاتین در شناسه‌ها، SKU، مبالغ خام و داده‌ی جدولی (برای دقت فنی و کپی‌پذیری).
- **واحد پول:** Toman به‌صورت عدد صحیح (D-010) — بدون اعشار، با جداکننده‌ی هزارگان.

### ۳.۲ کنتراست WCAG 2.2 AA

| قاعده | حد | اعمال |
|---|---|---|
| متن عادی | **≥ 4.5:1** | متن بدنه، برچسب‌ها، سلول‌های جدول |
| متن بزرگ (≥ 18.66px bold یا ≥ 24px) | ≥ 3:1 | تیترها، KPI |
| اشیای گرافیکی معنادار و مرز کنترل‌ها | **≥ 3:1** | آیکون معنادار، مرز فیلد ورودی، اندیکاتور وضعیت، حلقه‌ی focus |
| جداکننده‌های صرفاً تزئینی | الزام ۳:۱ ندارد؛ اما باید دیده شوند | خطوط جداکننده‌ی ردیف، پس‌زمینه‌ی نواحی |
| خطوط/میله‌های داده در نمودار | ≥ 3:1 نسبت به پس‌زمینه | نمودارهای تلمتری |
| برچسب متن داده در نمودار | ≥ 4.5:1 | مقادیر روی نمودار |
| حالت focus | حلقه‌ی دیدار ۲–۴px + کنتراست حالت ≥ 3:1 | همه‌ی عناصر تعاملی |
| حالت‌های خطا/موفقیت | ≥ 4.5:1 | پیام‌های فرم و وضعیت |

- کنتراست **در هر دو تم روشن و تاریک جداگانه** اندازه‌گیری می‌شود؛ فرض «مقادیر تم روشن در تم تاریک هم کار می‌کنند» ممنوع است.
- رنگ هرگز تنها حامل معنا نیست: هر وضعیت با **آیکون + متن/برچسب** همراه می‌شود.
- **تفکیک الزامی:** مرز فیلد ورودی و هر مرز حامل وضعیت، مرز «کنترل» است و باید ≥ 3:1 باشد؛ توکن‌های مرز این سند تزئینی‌اند و **نباید تنها مرز یک فیلد ورودی باشند**.

**قیدهای اعمال توکن:**

- **متن روی رنگ:** `#D97706` هرگز پس‌زمینه‌ی متن سفید نیست (۳.۱۹:۱ — زیر حد ۴.۵:۱)؛ روی آن فقط متن تیره `#0F172A` (۶.۵۹:۱) استفاده می‌شود. سه توکن دیگر با متن سفید مجازند، اما `#DC2626` در ۴.۸۳:۱ حداقلی است و **نباید** برای متن کوچک پرحجم یا ریز استفاده شود.

- **مرزها:** `#DBEAFE` روی `#F8FAFC` = **1.17:1** و `#334155` روی `#0B0F19` = **1.85:1** — این دو **تزئینی** هستند (جداکننده‌ی ردیف/ناحیه) و هرگز تنها مرز فیلد ورودی یا تنها حامل وضعیت نیستند؛ مرز کنترل‌ها از توکن‌های متن یا `#1E40AF` می‌آید.
- **تم تاریک:** رنگ‌ها به‌صورت desaturated/tonal بازتعریف می‌شوند، نه معکوس‌سازی مکانیکی.
- **قاعده‌ی منبع:** هیچ hex خامی در کامپوننت‌ها نوشته نمی‌شود؛ فقط توکن معنایی (`color-not-only`, `token-driven theming`).

### ۳.۴ اهداف لمسی (Touch Targets)

| زمینه | حداقل اندازه | مبنا |
|---|---|---|
| وب — هدف اشاره‌گر (pointer) | **≥ 24×24 CSS px** یا استثنای مستند | WCAG 2.2 AA (`web-target-size`) |
| موبایل — iOS | **≥ 44×44 pt** | Apple HIG |
| موبایل — Android | **≥ 48×48 dp** | Material |
| فاصله‌ی بین اهداف لمسی | **≥ 8px / 8dp** | Apple HIG / Material |
| ورودی فرم در موبایل | ارتفاع ≥ 44px | Apple HIG |
| عناصر تعاملی نمودار | ≥ 44pt ناحیه‌ی لمس | Apple HIG |

- اگر آیکون کوچک‌تر از حد است، **ناحیه‌ی لمس گسترده می‌شود** بدون تغییر اندازه‌ی بصری.
- واحدهای بومی (pt/dp) و واحد وب (CSS px) هرگز جای هم استفاده نمی‌شوند.
- چیدمان متراکم داشبورد مجاز است، اما **فشردگی هرگز نباید هدف لمسی را زیر حد ببرد**.

### ۳.۵ معناشناسی مستقل از رنگ

- هر وضعیت (سبز/زرد/قرمز) **همیشه** با آیکون و برچسب متنی همراه است.
- الگوی وضعیت استاندارد: `آیکون + برچسب فارسی + کد وضعیت انگلیسی` — مثال: `✔ تأییدشده (VERIFIED)`.
- نمودارها: هر سری داده علاوه بر رنگ، الگو/شکل/برچسب متمایز دارد.
- آیکون‌های تزئینی از درخت دسترس‌پذیری پنهان می‌شوند؛ آیکون‌های معنادار نام دسترس‌پذیر می‌گیرند.
- آیکون‌ها فقط SVG برداری — **استفاده از emoji به‌عنوان آیکون ساختاری ممنوع** است.
- بدون اتکا به hover: هر کنش حیاتی با کلیک/لمس در دسترس است.
- احترام به `prefers-reduced-motion`؛ همه‌ی انیمیشن‌ها در آن حالت کاهش می‌یابند.

## ۴. نقشه‌ی راه فازی (Phase Roadmap)

هر فاز مستقل، آزمون‌پذیر و fail-closed است. **هیچ فازی بدون تأیید مالک آغاز نمی‌شود.**

### Phase 1 — Foundation & Scaffold (پایه و اسکلت)

- راه‌اندازی Next.js (App Router) + Tailwind + Shadcn UI.
- پیکربندی RTL سراسری و تایپوگرافی `Vazirmatn`.
- لایه‌ی احراز هویت (Auth) با نشست fail-closed و بدون ذخیره‌ی توکن در مرورگر.
- اتصال مستقیم و **فقط‌خواندنی** به canonical PostgreSQL با استخر محدود.
- Master Layout: ناوبری کناری، هدر، تم روشن/تاریک، وضعیت اتصال زنده.
- **معیار پذیرش:** اسکلت RTL با کنتراست تأییدشده در دو تم، صفحه‌ی `/dashboard` زنده از SSOT، هیچ نوشتن مستقیمی وجود ندارد.

### Phase 2 — HITL Approval Center (مرکز تأیید انسانی)

- جدول کارت‌محور (card-table) تصمیم‌های AI: شدت، دسته، زمان، منبع، وضعیت.
- Drawer تفاوت (diff drawer) برای payload و override.
- لاگ استدلال (reasoning log) بازسازی‌شده از رویدادهای D-027 — بدون زنجیره‌ی فکری خام مدل.
- کنش‌های یک‌کلیکی: تأیید، اصلاح، رد، ارجاع — همه از مسیر موتور HITL (D-068/D-168).
- **معیار پذیرش:** هر کنش یک رکورد قابل ردیابی تولید می‌کند؛ بدون توکن، کنش غیرفعال است؛ صف از داده‌ی SSOT بازسازی می‌شود.

### Phase 3 — Telemetry & Gates (تلمتری و گیت‌ها)

- سلامت زنده‌ی سرویس‌ها (۱۰ کانتینر: `engine-local-*` و `engine-staging-*`).
- وضعیت گیت‌ها **V-01 تا V-10** با نمایش صریح PASS/FAIL/UNKNOWN و شاهد هر گیت.
- صف‌های n8n و Redis: عمق صف، نرخ پردازش، شکست‌ها.
- ردیابی شکست‌ها با trace context (D-121) و لینک به رکورد لجر.
- **معیار پذیرش:** هیچ گیتی هرگز بدون شاهد سبز نمایش داده نمی‌شود؛ کهنگی شواهد (stale) صریح است.

### Phase 4 — Inventory & Products (موجودی و محصولات)

- جدول داده‌ی متراکم (data-dense) با صفحه‌بندی سمت سرور.
- ویرایش درون‌خطی (inline edit) با اعتبارسنجی قبل از ارسال.
- وضعیت همگام‌سازی با WooCommerce (D-003، D-034–D-045) و Notion (D-060، D-156).
- نمایش provenance و حالت‌های داده‌ی ناموجود (D-011).
- **معیار پذیرش:** هر ویرایش از مسیر canonical/وب‌هوک می‌گذرد؛ تناقض همگام‌سازی صریح و fail-closed نمایش داده می‌شود.

### Phase 5 — AI Ops & Shared Memory Hub (عملیات هوش مصنوعی و حافظه‌ی مشترک)

- پایش حافظه‌ی مشترک (Walrus / D-142) — وضعیت لایه، نام‌فضاها، شمارش برداری.
- مشاهده‌پذیری عامل‌ها (agent observability): مسیرها، ابزارها، نرخ موفقیت.
- تحلیل مصرف توکن و هزینه با سقف‌های D-063/D-127.
- **قید:** لایه‌ی حافظه **PLANNED** است و هیچ اتصال زنده‌ای بدون گیت مالک (D-045) برقرار نمی‌شود؛ رابط فقط وضعیت را نمایش می‌دهد.
- **معیار پذیرش:** بدون اتصال، وضعیت `NOT_CONNECTED` صریح نمایش داده می‌شود — هرگز داده‌ی ساختگی.

### Phase 6 — Commerce & Analytics (تجارت و تحلیل)

- سفارش‌ها: چرخه‌ی عمر PLACED → VALIDATED → FULFILLING → COMPLETED (D-081).
- لاگ درگاه پرداخت — **بدون هیچ داده‌ی حساس کارت** (D-114/D-124).
- صدور فاکتور با مبالغ صحیح عددی (D-010).
- تحلیل تراکنشی: درآمد، نرخ تبدیل، سبد، بازگشتی‌ها.
- **قید:** ارائه‌دهنده‌ی پرداخت (تصمیم باز ۱۰) و حمل‌ونقل (تصمیم باز ۱۱) انتخاب نشده‌اند؛ فاز ۶ تا زمان انتخاب مالک، **dry-run** است.
- **معیار پذیرش:** هیچ مسیر پرداخت واقعی در رابط وجود ندارد؛ تحلیل‌ها از رویدادهای SSOT بازسازی می‌شوند.

## ۶. قیدهای امنیتی (Security Constraints)

1. **Fail-Closed در همه‌ی مرزها:** نبود شاهد، کهنگی شاهد، خطای تجزیه و پاسخ نامعتبر ⇒ شکست.
2. **بدون اعتبارنامه در رابط:** هیچ توکن، کلید، رمز، PAN یا داده‌ی شخصی در پاسخ‌ها، لاگ‌ها یا snapshotها ظاهر نمی‌شود (D-114/D-124).
3. **بدون نوشتن مستقیم در SSOT:** همه‌ی کنش‌های تغییردهنده از سرویس canonical یا وب‌هوک n8n عبور می‌کنند.
4. **بدون دورزدن گیت مالک:** رابط نه توکن می‌سازد، نه گیت را سبز می‌کند، نه فعال‌سازی را انجام می‌دهد (D-139).
5. **AST / دسترسی داده:** پرس‌وجوها پارامتری و allow-list شده‌اند؛ SQL خام پویا ممنوع.
6. **دسترس‌پذیری به‌عنوان قید امنیتی:** focus حلقه‌دار، ترتیب تب منطقی، برچسب‌های صریح، پشتیبانی صفحه‌خوان.

## ۷. معیار پذیرش کلی (Definition of Done)

- پیاده‌سازی وجود دارد و در مخزن قابل بازبینی است.
- آزمون‌ها/بررسی‌های مربوطه سبزند (شامل آزمون کنتراست و آزمون‌های fail-closed).
- حالت‌های خطا در نظر گرفته شده‌اند (نبود داده، کهنگی، قطع اتصال، خطای وب‌هوک).
- امنیت بازبینی شده است (redaction، مرزهای اقتدار، بدون اعتبارنامه).
- مستندات به‌روز شده‌اند (این سند، `TODO.md`، `DECISIONS.md`).
- تاریخچه‌ی Git قابل فهم است.
- تأیید انسانی لازم وجود دارد (مالک).
- هیچ مسئله‌ی بحرانی پنهان نشده است.
- شرط ورود فاز بعدی روشن است.

## ۸. مرزهای حفظ‌شده (Boundaries Preserved)

- این تصمیم **هیچ چیزی را نصب، متصل، مستقر یا فعال نمی‌کند**.
- `dashboard/` فعلی به‌عنوان snapshot ایستا دست‌نخورده باقی می‌ماند؛ Control Plane جانشین آن می‌شود، نه مکمل موازی آن.
- اعتبارنامه‌های زنده وجود ندارند و درخواست نمی‌شوند (D-045).
- فعال‌سازی تولیدی همچنان تنها با تصمیم صریح، یک‌بارمصرف و مالک‌محور (D-139) ممکن است.
- انتخاب ارائه‌دهنده‌ی پرداخت (تصمیم باز ۱۰) و حمل‌ونقل (تصمیم باز ۱۱) پیش‌نیاز فازهای تجاری است.
- حافظه‌ی مشترک (D-142) **PLANNED** است؛ رابط فقط وضعیت آن را نمایش می‌دهد.
