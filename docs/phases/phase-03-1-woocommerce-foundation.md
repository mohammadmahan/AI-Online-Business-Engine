## Purpose

contract before any implementation: the architectural role, the
identity/type/category/attribute/size/price/lifecycle/media/inventory

no connection to a real WooCommerce instance, no API credentials, no
keys, no production data changes, no n8n workflows, no
Python/JS/SQL/API code. Decisions D-034–D-045 are recorded in
`DECISIONS.md`; this document is their normative design record.

## 1. Architectural role of WooCommerce (D-003 — unchanged)

WooCommerce is the transactional Source of Truth for products,
variants, SKUs, prices, inventory, orders, customers, coupons, and
store state. The Product Master (our product data system: registries,
identifiers, provenance, lifecycle/publication states) remains the
**authoritative business configuration** for the fields it owns (see
the sync direction matrix, §14). WooCommerce receives that
configuration as a **projection** and owns all transactional state on
top of it.

Two-layer rule (the core contract of this batch):

1. **Canonical business layer (ours):** Product ID, Variant ID, SKU
   values, taxonomy/registry terms, price fields per D-024/D-025,
   lifecycle (D-022) and publication (D-023) states, provenance.
2. **Transactional projection layer (WooCommerce):** the platform
   representation of layer 1 plus everything transactional
   (orders, stock, customers) that only Woo may own.

Layer 1 never derives truth from layer 2, and layer 2 is never
hand-edited as a source for layer 1 (conflicts → human review, §16).

## 2. Identity mapping (D-034)

Five distinct identifiers; never conflated (extends D-014/D-015/D-017
to the WooCommerce context):

| Identifier | Nature | Generated by | Mutable? | Woo representation |
| --- | --- | --- | --- | --- |
| **Product ID** (`P00001`) | ours, business-facing | humans / approved tooling (D-017) | immutable, never reused | stored in Woo for reference; **NOT** the Woo product ID |
| **Variant ID** (UUIDv4) | ours, internal identity | approved tooling (D-017) | immutable, never reused | stored for reference; **NOT** the Woo variation ID |
| **SKU** (`P00001-BK-M`) | ours, business/inventory | humans / approved tooling (D-014/D-032) | immutable once created | Woo `sku` field (unique) |
| **WooCommerce product ID** | Woo-internal numeric | WooCommerce at creation | platform-owned | primary record ID |
| **WooCommerce variation ID** | Woo-internal numeric | WooCommerce at creation | platform-owned | variation record ID |

Rules:

- Our Product ID must never be confused with WooCommerce's numeric
  post/product ID, and our Variant ID must never be replaced by the
  SKU or by the Woo variation ID (D-015/D-017 unchanged).
- The SKU remains a business/inventory identifier; it is stored in
  Woo's `sku` field but is never Woo's internal identity.
- **Mapping registry (required):** a conceptual one-to-one registry
  connecting our identifiers to Woo identifiers:

  | Our identifier | Woo identifier |
  | --- | --- |
  | Product ID | Woo product ID |
  | Variant ID | Woo variation ID |
  | Color term | `pa_color` term ID (+ Latin slug) |
  | Size term (family-scoped) | `pa_size-{family}` term ID (+ Latin slug) |
  | Category term (primary + leaf) | Woo product category ID |

  The registry is written only by approved deterministic tooling at
  first successful creation/read-back; conflicts route to human
  review; it is never hand-maintained and never fuzzy-matched. The
  registry does **not exist yet** — it is a Phase 3 implementation
  requirement (documented here, not implemented).
- The Woo numeric IDs are internal technical identifiers: they may be
  recreated only as new records (never renumbered/reassigned) and are
  never used as our business identity. If a Woo record is lost, the
  registry linkage is repaired by a human decision, not silently.

## 3. Simple vs variable product (D-035)

Deterministic mapping from D-018 (exactly two Woo product types; no
third type is introduced):

| Active axes (D-018) | Our product | WooCommerce mapping |
| --- | --- | --- |
| zero | simple product (SKU = Product ID) | Woo product type `simple`, SKU = Product ID |
| Color only | variable (one attribute) | Woo type `variable`, attribute `رنگ` (pa_color); one variation per color |
| Size only | variable (one attribute) | Woo type `variable`, the product's family size attribute; one variation per size |
| Color + Size | variable (two attributes) | Woo type `variable`, attributes `رنگ` + family size attribute; one variation per color+size combination |

Rules:

- Active axes are read from our product data deterministically (D-033
  encoding); a product with ≥ 1 active axis is `variable` regardless
  of variation count (even a single-variation variable product stays
  `variable` — no demotion heuristic).
- Each of our variants maps 1:1 to a Woo **variation**; variation
  identity is keyed through the mapping registry (§2), never by
  matching names.
- Product-level-only differences are separate products (D-018 rule 4)
  and therefore separate Woo products — never variations.
- Inseam and every other non-Color/Size attribute never create
  variations (D-018/D-031 unchanged).

## 4. Category mapping (D-036)

The exact Batch 1 tree (D-031) maps to a two-level WooCommerce product
category hierarchy — the simplest faithful mapping:

| Batch 1 term | WooCommerce category |
| --- | --- |
| پوشاک زنانه | top-level category |
| پوشاک مردانه | top-level category |
| each women's leaf (مانتو، شومیز، … 12) | child category **under** پوشاک زنانه |
| each men's leaf (تیشرت، پیراهن، … 8) | child category **under** پوشاک مردانه |

- **Duplicate leaf names stay distinguishable** (تیشرت زنانه vs
  تیشرت مردانه): they are separate child categories under their own
  parent — identical display labels, distinct category records. No
  leaf is merged or shared across primaries (a category term belongs
  to exactly one primary, D-031).
- The D-033 physical columns map 1:1: `دسته‌بندی اصلی` → parent
  category; `زیردسته` → child category under that parent. The
  primary–leaf pairing is validated exactly (primary-scoped leaf
  matching); a leaf under the wrong primary is INVALID.
- No extra categories are created; the hierarchy mirrors D-031
  verbatim. Category changes remain owner-gated (D-031).
- Category is **not** a variant-defining axis: no Woo attribute is
  created from it; it is the Woo category taxonomy only.

## 5. Attribute architecture (D-037)

WooCommerce representation of the approved attribute set:

| Attribute | Woo representation | Level | Controlled? | Status | Reason |
| --- | --- | --- | --- | --- | --- |
| Color (رنگ) | **one global attribute** `pa_color`, 25 terms | variation-defining | controlled (D-031 terms) | seed required | D-018 axis |
| Size (سایز) | **one global attribute per family** — `pa_size-alpha`, `pa_size-numeric`, `pa_size-waist` | variation-defining | controlled (D-031 terms) | seed required | family-scoped semantics (below) |
| Size Family (خانواده سایز) | **not** a customer-facing attribute | product-level context | controlled (3 families) | internal mapping context | selects which size attribute the product uses; a customer sees the size, not the family (D-020 rule 3/4) |
| Brand, Material, Pattern, Style, Season, Usage, Collar, Sleeve, Length, Closure, Fit | **not created** as Woo global attributes now | product-level informational | free text (outside Registry v1, D-029) | representation OPEN | promotion into controlled vocabularies is a separate owner decision (D-019/D-031); silently making all of them global Woo attributes would imply vocabulary decisions the owner has not made |

Rules:

- Only Color and Size are variation attributes (D-018); every other
  approved attribute stays product-level informational data.
- **Color terms:** term display name = the Persian canonical value;
  term slug = stable Latin slug (lowercase of the D-032 code —
  deterministic, e.g. `bk`, `wht`, `gy1`). The D-032 code remains our
  canonical code; the Woo term ID is only a mapped technical id
  (registry, §2). No aliases, no new colors, no fuzzy matching.
- **Size-family strategy (critical design point):** WooCommerce
  attributes are flat — one shared `pa_size` attribute would collapse
  Numeric `42` and Pants Waist `42` into a single term, destroying
  D-020/D-032 family-scoped semantics. Therefore **one global size
  attribute exists per approved family**; a product uses exactly the
  attribute of its declared family (product-level context, D-020
  rule 3), and its variations use that attribute's terms. Numeric 42
  (in `pa_size-numeric`) and Pants Waist 42 (in `pa_size-waist`) are
  distinct Woo terms in distinct attributes — no merge, no equivalence,
  no automatic conversion. Alpha term slugs are the lowercase D-032
  codes (`xs`, `s`, `m`, `lg`, `xg`, `xxg`, `3xg`, `4xg`); display
  names stay the conventional labels (`L`, `XL`, …) per D-020 rule 4.
- The taxonomies' Latin slugs are **internal identifiers**, not the
  SEO URL decision — SEO slug language remains OPEN (D-016.M) and is
  untouched by this batch.
- Term creation in Woo is part of the one-time seed of the owner-
  approved registries; runtime term creation does not exist (D-019:
  humans create terms; AI proposes only).

## 6. Price mapping (D-038)

Field mapping from D-024/D-025 (semantics unchanged; numeric Toman,
D-010):

| Our field (D-024/D-025) | Level | Woo field |
| --- | --- | --- |
| List price | product | `regular_price` |
| Variant price override | variation | variation `regular_price` |
| Sale price (+ validity end) | product or variation | `sale_price` (+ the sale-end date field; no start-date field is used — D-025 has no start scheduling) |
| Effective price | derived (D-024 rule 4) | displayed by Woo from the written fields; canonical resolution remains ours |

Pre-write validation (before any price is written to Woo):

- numeric Toman integers only; formatted strings rejected (D-010);
- sale < applicable base; sale ≥ base rejected, never clamped;
- zero/negative effective price invalid; expired sales ignored;
- unresolved base price is never written or guessed (D-024 rule 5);
- AI never creates or changes a production price (Red tier; §18).

**Known divergence (documented, not hidden):** our effective-price
precedence is *valid variant sale → valid product sale → variant
override → product list price*. WooCommerce's native display fallback
for a variation is commonly *variation sale → variation regular
price*, and a parent-level sale does not reliably cascade onto
variations that carry their own prices. In the case "product-level
sale active + variant override set + no variant-level sale", Woo's
native display can therefore differ from the D-024 resolution.
(Exact native behavior is an **implementation-time verification
point**; this batch does not pretend the specification of Woo's
internal price resolution is final.)

Candidate resolutions (owner decision required — **OPEN sub-gate of
D-038**):

- **A) Materialize at sync:** approved tooling writes the D-024/D-025
  effective sale/base resolution into the variation fields Woo
  actually displays, at each affected change; base/list fields are
  never mutated — only the sale/override projections are set to match
  the canonical resolution.
- **B) Config constraint:** product-level sales are allowed only on
  products without variant price overrides (deterministic, narrower).
- **C) Accept Woo-native display** and surface divergences for human
  review at sync time.

Until the owner chooses, the mapping table above is the contract and
the divergence case is flagged at validation; no silent resolution
occurs. D-024/D-025 themselves are untouched by all three options.

## 7. Lifecycle & publication projection (D-039)

Our two state machines (D-022/D-023) **remain canonical**; WooCommerce
cannot represent both in its single post `status` field, so Woo
receives a **projection** of the canonical states:

| Product status (D-022) | Publication (D-023) | Woo projection |
| --- | --- | --- |
| `draft` | any | **no Woo record yet** (creation happens when the product enters `active`) |
| `active` | `unpublished` | Woo record created/kept hidden (non-published status) |
| `active` | `in_review` | hidden (non-published status) |
| `active` | `published` | **published** (public) — only after the Red-tier human approval, executed by approved tooling |
| `active` | `withdrawn` | hidden, record preserved (non-published status) |
| `archived` | any | hidden, record preserved — **never deleted** (D-022; deletion is a destructive operation, RULES §22) |

Rules:

- No new business state is invented; the projection table is a
  deterministic rendering of D-022/D-023 states, and the canonical
  states live only in our layer. A native Woo status is **not**
  claimed to be equivalent to a D-022/D-023 state — it is a projection
  of one.
- Transitions are executed on Woo only after the corresponding
  human-approved canonical transition (D-022/D-023 authority rules);
  forbidden canonical transitions (e.g. `withdrawn → published`,
  `archived → active`) are impossible in the projection too.
- AI never executes any lifecycle/publication transition (§18).
- The exact field-level combination (status vs catalog-visibility
  fields per Woo version) is an implementation-time verification
  point; the *contract* above is the normative behavior.

## 8. Media mapping (D-040)

Mapping of the D-033 media references (publication minimum ≥ 1 image,
D-021):

- First reference → Woo **primary/featured** product image; remaining
  references → gallery images **in the given order** (`|`-separated
  order preserved).
- **Alt text:** deterministic default = the product name; richer alt
  text may later come from Media records / AI suggestions (Yellow
  tier, provenance-tagged). Nothing is invented.
- The references are **references, not binaries**: the Excel cell and
  our Media entity store references; whether the implementation
  uploads binaries into the Woo media library or attaches external
  URLs is an **OPEN storage decision** (no provider chosen, nothing
  uploaded, no media infrastructure in this batch).
- Media sync is executed by approved tooling after human promotion,
  like all other writes.

## 10. WooCommerce API contract (D-043 — conceptual)

Resource areas and operations (official WooCommerce REST API family;
D-012 ladder: official API first — consumed via n8n or approved
tooling; **no code written and no API called in this batch**):

| Resource area | Operations | Purpose | Idempotency | Source-of-truth direction | Human approval | Error behavior |
| --- | --- | --- | --- | --- | --- | --- |
| Products | create / update / read | push product records; read-back confirmation | mapping-registry keying (§2); create only if registry has no entry (plus deterministic lookup); D-027 event per operation | ours → Woo (business fields); Woo → registry (IDs only) | record creation follows human-promoted flows; delete = Red tier, destructive (RULES §22) — prefer hide/archive over delete | §12 table |
| Variations | batch create / update / read | push variants of variable products | per-variant registry keying | ours → Woo; IDs back to registry | same as products | §12 table |
| Product categories | one-time seed / read | create the D-036 hierarchy | create-if-absent by exact (parent, child) pair; never name-fuzzy-matched | ours → Woo (exact D-031 tree) | seed is owner-approved (D-031); no runtime category creation | §12 table |
| Product attributes | one-time seed / read | create pa_color + the three size attributes (D-037) | create-if-absent by exact slug | ours → Woo | seed is owner-approved (D-031/D-032 terms) | §12 table |
| Attribute terms | one-time seed / read | create the 25 color terms + family-scoped size terms | create-if-absent by exact slug within the attribute | ours → Woo; term IDs back to registry | terms are owner-approved (D-019/D-031/D-032); no runtime term creation | §12 table |
| Media | upload or reference (per §8) | attach product images | registry/deterministic reference keying | ours → Woo | follows the human-promoted product flow | §12 table |

Contract rules:

- Every write operation is idempotent under D-027 (each operation is
  an event with a (source system, event ID) key) and keyed by the
  mapping registry under D-017 (identifier-level).
- **No credentials exist and none are requested in this batch.** The
  authentication model (key/secret over HTTPS) is recorded as the
  expected mechanism and verified at implementation.
- Exact endpoint versions and field-level API details are
  **implementation-time verification points** — not finalized here.
- Delete operations on products/variations/terms are destructive
  operations (RULES §22): human approval required; the standing
  preference is deactivate/hide/archive instead of delete (D-022
  archived semantics).

## 11. n8n ↔ WooCommerce boundary (D-042)

Responsibility split (unchanged from the approved architecture):

| System | Responsibility |
| --- | --- |
| Product Master | canonical business data (identity, taxonomy, price fields, lifecycle/publication states, provenance) |
| n8n | orchestration: triggers, sequencing, retries, event records, error routing, notifications — **not** a data store, **not** a source of truth |
| WooCommerce | ecommerce transaction/data execution and transactional state |
| AI Runtime | proposal/enrichment/decision support (Yellow tier, provenance-tagged) |
| Human | business-critical authority (approvals, Red-tier actions) |

Synchronization directions (explicit, per-field — **no default
bidirectional field sync**):

| Flow | Fields | Authoritative source | Trigger | Validation | Approval | Conflict handling |
| --- | --- | --- | --- | --- | --- | --- |
| Product Master → Woo | identity, taxonomy, attributes, prices, descriptions/SEO, media refs, publication projection | Product Master | human-promoted sync run (D-027 event) | full pre-write pipeline (§6, §10) | human promotion of the run; Red tier for publish and price-affecting writes | registry/conflict mismatch → human review, never silent overwrite |
| Woo → Product Master | created Woo IDs (registry write-back) | Woo (IDs only) | after each successful create | ID format/consistency | automatic (tooling, logged) — IDs are technical facts | duplicate/ambiguous → human review |
| Woo → operational views (future phases) | stock, orders, customers (read-only references) | Woo | scheduled/event (future) | read-only; minimization (RULES §28) | n/a (reads) | n/a |
| Woo → Product Master (field sync of PM-owned fields) | — | **not permitted** | — | — | — | Woo-side manual edits of PM-owned fields are divergences: detected on read-back comparison and routed to human review; no silent overwrite in either direction |

Woo-owned transactional fields (stock, orders, customers, coupons) are
never written by Product Master flows (§9, D-016.I open).

## 12. Error handling (D-044)

Deterministic classification (retry policy counts/backoff are set per
workflow at Phase 5 — no arbitrary numbers invented here):

| Case | Class | Handling |
| --- | --- | --- |
| WooCommerce unavailable / network error / timeout before response | retryable (bounded) | safe retry under the same D-027 event ID; backoff per workflow spec |
| timeout with ambiguous write outcome | retryable after reconciliation | read-back/registry check **before** any re-create; never blind re-create |
| rate limiting | retryable | respect the provider's backoff signal; same event ID |
| partial response | retryable | retry the operation; validate by read-back |
| authentication failure | non-retryable | halt, alert; credential/config fix is a human action (RULES §16) |
| validation failure (our pipeline) | non-retryable until corrected | data error — human corrects the source data; never auto-corrected |
| duplicate resource (registry absent, deterministic lookup finds one) | non-retryable | flag for human review — no silent adoption, no silent overwrite |
| conflicting resource (same identity, different data) | non-retryable | data-integrity conflict → human review (D-017/D-027 conflict rule) |
| malformed response | non-retryable | log, alert; contract/protocol error — human investigation |
| immutable identifier mismatch (registry vs Woo) | non-retryable | integrity error → human review; never silently relinked |

Human review exists for every data-integrity conflict; errors are
never hidden or swallowed (RULES §24, §41).

## 13. Idempotency (D-044)

- **Identifier-level (D-017):** Product ID / Variant ID / SKU remain
  the identity keys of our data; Woo identifiers are mapped through
  the registry (§2). Create operations run only when the registry
  shows no existing linkage (with deterministic lookup as a second
  guard); duplicates are flagged, never merged.
- **Event-level (D-027):** every sync operation is an event with a
  (source system, event ID) key; identical repeats are skipped and
  logged; conflicting repeats are integrity errors → human review;
  terminal states are never re-entered.
- The two mechanisms remain distinct and complementary, exactly as
  approved (DATA_MODEL §8b, §9.2, §13.5).
- The mapping registry is a **Phase 3 implementation requirement**
  (does not exist yet); until it exists, no sync implementation may
  start.

## 15. AI authority (unchanged — verified)

All Phase 2 boundaries are preserved verbatim in the WooCommerce
context. AI **may**: suggest mappings, draft descriptions/enrichment,
recommend categories/attributes, analyze errors, prepare/suggest
actions (Yellow tier, provenance-tagged). AI may **not**

syncs, or resolve business-critical conflicts without human approval.

## 16. Critical conflicts and open questions (explicit)

1. **Size families sharing display values** — resolved by design:
   one global size attribute per family (D-037 §5); Numeric 42 and
   Pants Waist 42 remain distinct Woo terms. No conflict remains.
2. **Product lifecycle vs Woo post status** — resolved by projection
   (D-039 §7): canonical states stay ours; Woo `status` is a
   projection. Field-level projection verified at implementation.
3. **Publication state vs Woo visibility** — same projection table;
   publish writes occur only after Red-tier human approval.
4. **Product ID vs Woo numeric product ID** — resolved: distinct
   concepts, mapped via the registry (D-034).
5. **Variant ID vs Woo variation ID** — resolved: distinct, mapped;
   the Variant ID is never replaced by SKU or variation ID.
6. **SKU vs Woo internal identity** — resolved: SKU is the `sku`
   field (business identifier), never Woo's internal identity.
7. **Product-level vs variation-level attributes** — resolved: only
   Color/Size are variation attributes (D-018/D-037); everything else
   product-level informational.
8. **Archived products** — resolved: Woo record hidden, preserved,
   never deleted (deletion is destructive, RULES §22).
9. **Media references** — mapping resolved (D-040); **storage
   mechanism OPEN** (upload vs external URL; no provider).
10. **Bidirectional synchronization** — resolved: per-field direction
    matrix (D-042 §11); no default bidirectional field sync; Woo-side
    edits of PM-owned fields are divergences → human review.
11. **Price divergence (native Woo fallback vs D-024 precedence)** —
    **REAL conflict, OPEN**: options A/B/C in §6; owner decision
    required before sync implementation. Validation flags the case;
    nothing resolves it silently.
